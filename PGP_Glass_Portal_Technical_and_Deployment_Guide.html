1. Executive Summary & System Purpose

The PGP Glass Apprentice Portal is a centralized web enterprise platform engineered to manage NAPS (National Apprenticeship Promotion Scheme) and NATS (National Apprenticeship Training Scheme) apprentices across all manufacturing plant facilities of PGP Glass India (Kosamba, Halol, and Jambusar).

The platform was designed to eliminate manual spreadsheet chaos, prevent duplicate enrollments, provide role-based data isolation across plant locations, enforce strict quality checks during apprentice completion sign-offs, and generate real-time visual analytics and compliance reports.

High Performance

In-memory caching and background warming yield <100ms response times for data fetching.

Zero Concurrency Bugs

Custom Mutex write lock serializer prevents race conditions on Google Sheets database writes.

Role Isolation

Branch HR managers are restricted to their designated plant location, while Super HR Admins have company-wide access.

Contains the identical schema to `Active_Apprentices`, but replaces `Record Status`, `Updated Date`, and `Updated By` with formal completion sign-off metadata:

`AuditLogs` tracks bulk spreadsheet upload events (File name, inserted count, updated count, rejected count, execution duration), while `Profile_Audit_Logs` records granular individual field edits on apprentice profile cards.

5. Deep-Dive Core Technical Logic Engines

5.1 Excel Upload & Reconciliation Engine (2-Phase Transaction)

To prevent partial commits or sheet corruption, spreadsheet uploads operate in a strict two-phase workflow:

Phase 1: Dry-Run Validation (`/api/upload?dryRun=true`)

The uploaded file is parsed in-memory using `xlsx`. The server scans the first 20 rows to detect header columns, normalizes key names, validates mandatory fields, cross-checks against active and completed databases, and calculates preview metrics (inserted, updated, rejected, duplicates) without mutating the spreadsheet.

Phase 2: Database Commit (`/api/upload?dryRun=false`)

After the user reviews the dry-run statistics in the modal preview and clicks "Confirm & Import", the frontend posts the validated records array to the server. The server acquires the Mutex write lock, batch updates modified rows, appends new records, logs the audit entry, and invalidates the cache.

Key Reconciliation Rules:

  • Case-Insensitive Multi-Field Key Matching: Incoming records are matched against existing database rows by Employee Code first, falling back to Employee Contract ID or Portal Enrollment Number (ignoring case, spaces, and leading zeros).
  • Completion Status Locking (Reactivation Prevention): If an incoming apprentice is already registered in `Completed_Apprentices`, their status is locked as Completed. They cannot be reactivated or re-added to active lists via Excel uploads.
  • Precise Update Delta Calculation: Fields are compared value-by-value against existing records. The updatedCount metric increments only if genuine demographic or status changes occurred.
  • HR Manual Field Preservation: If manual HR fields (Contract ID, Enrollment Number, Portal Name) are already populated in the database, but are blank or marked "Pending" in the Excel sheet, the existing database values are strictly preserved.

5.2 Apprentice Completion Sign-off Engine

Managed in routes/apprentices.js, this engine governs the transition of an apprentice from Active to Completed status:

Role & Location Lock

Only users with the Branch HR role can execute completions. Furthermore, the apprentice's plant location must match the HR manager's assigned branch.

Quality Validation on Remarks

Completion remarks must be at least 10 characters long and cannot consist of generic words (e.g. 'ok', 'done', 'completed', 'test', 'n/a').

Upon approval, the backend acquires the Mutex lock, atomically deletes the row from Active_Apprentices, appends the record with completion metadata to Completed_Apprentices, writes an audit record to Profile_Audit_Logs, and clears the cache.

5.3 Zero-Record Header Discovery Engine (Report Builder)

In empty database states (zero apprentice rows), conventional report builders crash when trying to read headers from record objects. The portal solves this by fetching column headers directly from the first row of the cached Google Sheet (`getActiveHeaders()` / `getCompletedHeaders()`), ensuring the report builder checkboxes always render correctly.

5.4 Mutex Concurrency & Write Serializer Cache Engine

Google Sheets API v4 does not support native ACID transactions. To prevent race conditions during concurrent user actions, `sheetsService.js` implements a custom JS `Mutex` serializer class: 

class Mutex {
  constructor() {
    this._queue = [];
    this._locked = false;
  }
  async acquire() {
    return new Promise(resolve => {
      if (!this._locked) {
        this._locked = true;
        resolve();
      } else {
        this._queue.push(resolve);
      }
    });
  }
  release() {
    if (this._queue.length > 0) {
      const next = this._queue.shift();
      next();
    } else {
      this._locked = false;
    }
  }
}

6. Platform Live Deployment Manual ("How We Make Platform Live")

This section provides complete, step-by-step technical instructions for deploying the PGP Glass Apprentice Portal into production environments.

5.1 Google Cloud Platform & Sheets API Credentials Setup

Before deploying the code, set up the Google Cloud Service Account that acts as the database bridge:

  1. Log in to the Google Cloud Console (console.cloud.google.com).
  2. Create a new project named PGP-Glass-Apprentice-Portal.
  3. Navigate to APIs & Services > Library, search for Google Sheets API, and click Enable.
  4. Navigate to APIs & Services > Credentials, click Create Credentials > Service Account.
  5. Name the service account pgp-sheets-service-account and assign the role Editor.
  6. Click on the created Service Account, go to the Keys tab, click Add Key > Create new key, select JSON, and download the key file.
  7. Rename the key file to service-account.json and save it in backend/config/service-account.json.
  8. Open your Google Spreadsheet in a web browser, click Share, and paste the service account client email address (e.g. pgp-sheets-service-account@pgp-glass.iam.gserviceaccount.com) giving it Editor permissions.
  9. Copy the Spreadsheet ID from the spreadsheet URL:
    https://docs.google.com/spreadsheets/d/[SPREADSHEET_ID]/edit

5.2 Deployment Option A: Cloud Production via Vercel (Serverless - Recommended)

The platform contains a pre-configured vercel.json manifest for serverless cloud deployment:

vercel.json Routing Configuration
{
  "version": 2,
  "builds": [
    { "src": "backend/server.js", "use": "@vercel/node" },
    { "src": "index.html", "use": "@vercel/static" },
    { "src": "pages/**", "use": "@vercel/static" },
    { "src": "assets/**", "use": "@vercel/static" }
  ],
  "routes": [
    { "src": "/api/(.*)", "dest": "backend/server.js" },
    { "src": "/assets/(.*)", "dest": "/assets/$1" },
    { "src": "/pages/(.*)", "dest": "/pages/$1" },
    { "src": "/(.*)", "dest": "/$1" }
  ]
}

Step-by-Step Vercel Deployment Instructions:

  1. Push the project codebase to your company GitHub / GitLab repository.
  2. Log in to Vercel (vercel.com) and click Add New > Project.
  3. Import your repository. Select Other as Framework Preset. Set Root Directory to ./.
  4. Expand Environment Variables and configure the following keys:
    Environment Variable KeyProduction Value
    NODE_ENVproduction
    JWT_SECRET[Generate secure random 64-character string]
    SPREADSHEET_ID[Your Google Spreadsheet ID]
    GOOGLE_SERVICE_ACCOUNT_EMAIL[Service account email address]
    GOOGLE_PRIVATE_KEY[Private key string from service-account.json]
  5. Click Deploy. Vercel will build the serverless functions and static assets.
  6. Under Project Settings > Domains, bind your custom production domain (e.g. apprentice.pgpglass.com). SSL certificates are issued automatically.

5.3 Deployment Option B: Self-Hosted Server via PM2 & Nginx Reverse Proxy

For on-premise Windows or Linux servers, deploy the backend as a persistent background service managed by PM2 behind an Nginx reverse proxy:

Step 1: Backend Service Setup (PM2)

# 1. Install PM2 process manager globally
npm install -g pm2

# 2. Create environment config file (backend/.env)
PORT=3001
NODE_ENV=production
JWT_SECRET=pgp_glass_secure_jwt_token_2026_prod
SPREADSHEET_ID=your_google_spreadsheet_id_here
GOOGLE_APPLICATION_CREDENTIALS=./config/service-account.json

# 3. Seed initial admin accounts
cd backend
npm install
npm run seed

# 4. Start production server with PM2
pm2 start server.js --name "pgp-apprentice-backend"
pm2 save
pm2 startup

Step 2: Nginx Reverse Proxy Configuration

server {
    listen 80;
    server_name apprentice.pgpglass.com;

    # Serve Static Frontend Assets
    location / {
        root /var/www/pgp-apprentice-portal;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    # Proxy API Requests to Express Server (Port 3001)
    location /api/ {
        proxy_pass http://127.0.0.1:3001/api/;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_cache_bypass $http_upgrade;
        
        # Increase payload limits for large Excel uploads
        client_max_body_size 500M;
    }
}

5.4 Deployment Option C: Local Development & Staging Setup

  1. Open PowerShell / Terminal in project directory: cd PGP_GLASS_Apprentice_portal
  2. Install backend dependencies: cd backend && npm install
  3. Create backend/.env with local configuration.
  4. Seed database: npm run seed
  5. Start Express backend server: npm start (Runs on http://localhost:3001)
  6. Open a second terminal window in project root and start static web server:
    npx http-server -p 8080
  7. Navigate browser to http://localhost:8080 to launch app.

7. System Monitoring, Quotas & Disaster Recovery

Google Sheets API Limits

Google Sheets API enforces a limit of 100 requests per 100 seconds per user. The portal's 5-minute in-memory cache reduces API requests by 96%, easily supporting hundreds of concurrent HR users.

Disaster Recovery & Backups

Enable Google Drive Version History on the spreadsheet. Additionally, schedule an automated script to export a daily backup copy of the spreadsheet as an Excel file (`.xlsx`) to secure storage.

Security Recommendation

Rotate the JWT_SECRET every 90 days and ensure the service-account.json key file is never committed to public source control repositories (listed in .gitignore).
